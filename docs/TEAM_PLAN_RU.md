## Оценка и отправки

TRAIN (2021-07–2025-06) содержит правильные ответы; sample — июнь 2025. LIVE (2025-07–12) даёт обратную связь; учитывается лучшая оценка. FINAL (2026-01–06) появляется в 18:00: ровно один принятый валидный результат, заменить его нельзя. Без FINAL команда не входит в финальный рейтинг. Результат скрыт до 20:30. При равенстве FINAL выигрывает более ранняя отправка; в LIVE — более раннее достижение оценки.

Score = 100 × (0.5 × Allocation F1 + 0.3 × Transaction accuracy + 0.2 × Exception macro-F1).

- 50%: правильные пары платёж–счёт с верной суммой; лишние неверные связи тоже ухудшают результат.
- 30%: полностью верные операции, включая набор счетов, суммы, исключения и категории.
- 20%: среднее качество по классам непустых исключений. Редкие классы нельзя полностью игнорировать.
- Допуск суммы: max(0.01, 0.5% от эталонной суммы). Это допуск оценки, а не разрешение произвольно прощать недоплату.
- Точность по денежному объёму показывают отдельно; собственного веса в формуле у неё нет.
- Ориентиры сайта ≈19 для простого решения и ≈61 для хорошо проработанных правил не являются гарантией нашего результата.
- Не чаще одной отправки в 3 минуты, до 20 в день на фазу. Запрос URL загрузки уже расходует слот. Ошибка формата расходует обычный слот, но не единственную валидную FINAL-оценку.
- CSV UTF-8 с заголовком, допустим gzip; максимум 60 MB В РАСПАКОВАННОМ ВИДЕ и 3 млн строк. Опубликованный scorer использует 60 × 1024 × 1024 байт; планируем запас ниже 60 млн байт.
- При отправке скриптом: резервировать слот, загрузить файл, запустить оценку, проверить конечный статус. Опрос не чаще раза в 5 секунд, зал использует общий IP.

## CSV: обязательные проверки

Ровно пять колонок: bank_txn_id,item_id,amount,category,exception. Выбираем канонический формат: запятые, точка в сумме, 2 десятичных знака. Валидатор также допускает некоторые альтернативы, но они нам не нужны.

- Покрыть все bank_txn_id целевой фазы: пропущенные считаются ошибкой.
- По одной строке на пару платёж–счёт; повторов пары быть не должно.
- Если счетов нет — одна строка с пустыми item_id и amount и разрешённой category.
- Нельзя смешивать строки со счетами и строку категории для одного платежа.
- amount — погашаемая сумма в валюте СЧЁТА, положительная, включая credit notes и возвраты. Не копировать знак банковской операции.
- На строках счетов category пустая. exception только из списка или пустая.
- Проверять известность идентификаторов и принадлежность операции нужной фазе.
- Не добавлять в итоговый CSV confidence, объяснения и источники. Их сохранять отдельно для проверки и демо.

## Политики сопоставления: все ключевые случаи

| Случай | Сумма и результат |
|---|---|
| Обычная оплата | Открытый остаток счёта; исключение пустое |
| Credit note зачтена | Отдельная строка, положительная сумма; исключение пустое |
| PARTIAL | Фактически погашенная часть; остаток остаётся открытым |
| SHORT_DISCOUNT | Полный остаток, если скидка предусмотрена условиями и booking_date не позже issue_date + discount_days + 3 дня; скидка считается от полной суммы с округлением |
| Поздняя скидка | PARTIAL, разница остаётся долгом |
| SHORT_BANK_CHARGES | Полный остаток для комиссии посредника в переводе из-за пределов SEPA, одновременно ≤60 EUR эквивалента и ≤2% счёта; выше — PARTIAL |
| SHORT_WITHHOLDING | Полный остаток, налог удержан плательщиком; встречаются 1.25%, 1.5%, 10% в MX/BR/MA |
| SHORT_DISPUTE | Реально применённая сумма, документированная спорная часть остаётся открытой |
| OVERPAYMENT | Полный открытый остаток; лишние деньги не создают дополнительную строку |
| DUPLICATE_PAYMENT | Повторно заплаченная сумма по уже погашенному счёту |
| RETURNED | Сумма, которую возврат снова делает открытой; все затронутые счета |
| UNIDENTIFIED | Без счёта; и category, и exception равны UNIDENTIFIED |
| FX_DIFFERENCE | При другой валюте банковской операции: полный остаток в валюте счёта; курс банка может отличаться от справочного |

При FX код FX_DIFFERENCE заменяет пустой код, SHORT_DISCOUNT, SHORT_WITHHOLDING, SHORT_BANK_CHARGES для полностью закрытых invoice-строк. PARTIAL/SHORT_DISPUTE сохраняются; у credit-note строк исключение пустое. Курсы: единиц валюты за EUR, в выходной брать последний доступный рабочий день. Не путать 3% FX-допуск с 0.5% допуском суммы в scorer.

Последний взнос, выплата ранее удержанной гарантии, погашение остатка после partial/dispute и повторно успешно предъявленный direct debit идут без исключения.

Операции без счетов: комиссии, проценты, зарплата, соцвзносы, налоги/возвраты, кредиты, лизинг, FX-сделки, cash pool, межфирменные и внутренние переводы, авансы, возвраты клиенту/от поставщика, корпоративные карты, страхование, банковские сторно, unidentified — точные 21 коды в masters/categories.csv.

Особые правила:

- Карточная выплата закрывает заказы по gross; удержание эквайера не является исключением. Отдельная строка банковской комиссии — BANK_FEES.
- Ошибочная банковская операция и её сторно обе BANK_REVERSAL.
- Проформа не счёт: её оплата CUSTOMER_ADVANCE. Последующая оплата финального счёта за вычетом аванса — PARTIAL по политике организаторов.
- Возврат переплаты: CUSTOMER_REFUND/SUPPLIER_REFUND; возврат по supplier credit note закрывает APC, это не категория.
- Плательщик может быть материнской компанией, фактором, confirming-банком или агентством. Искать реального должника.
- ES00 оплачивает часть счетов ES01/ES02/PT01: не отбрасывать их только из-за несовпадения entity банковского счёта и invoice.
- Direct-debit, card, cheque и payment-run реестры раскрывают состав агрегированного платежа; per-transfer платеж ищется по end_to_end_id; confirming группируется по сроку.
- Remittance advice может прийти позже денег, содержать номера клиента и поменять формат.
- Номер на документе не равен item_id. Учитывать обрезки, отсутствие префиксов/нулей, опечатки, PO, старые имена и IBAN.
- Одинаковые суммы у одного клиента: FIFO по дате выставления среди открытых счетов; указанный месяц услуги приоритетнее FIFO. Месяц услуги бывает только в PDF.
- Аннулированный и заменённый счёт: платить новый, даже если текст ссылается на старый. Старый и аннулирующая credit note не закрываются банковским платежом.
- PDF содержит рассрочки, гарантии, вычет авансов, замену счетов, правила зачёта/выплаты credit notes, передачу фактору, новые реквизиты.
- Возврат открывает остаток повторно; re_presentation=Y означает повторное предъявление.
- Совпадение только суммы недостаточно: есть специально похожие неопознанные платежи.
- Проводки и расчёт бухгалтерской прибыли/убытка от FX не нужны.

## Как строить решение

1. Использовать готовую bank_transactions.csv.gz: она нормализована и очищена от дублей. Сырые выписки сохранять для диагностики, не делать их парсинг первым этапом.
2. Собрать каталог AR/AP/credit notes и индексы номеров, сторон, IBAN; для LIVE/FINAL инициализировать остатки из open_items_at_start, затем добавить документы фазы. Исторические документы могут требоваться для контекста, возвратов и дублей; не считать все исторические invoices открытыми.
3. Модули выдают кандидатов и доказательства; A выбирает одну согласованную интерпретацию целого платежа. Нельзя просто склеить CSV четырёх участников.
4. Сначала точные документы и реестры, затем надёжные сопоставления сторон/номеров/сумм, затем менее уверенные случаи. Порядок приоритетов подтверждаем на TRAIN.
5. Вести остатки и историю по booking_date: погашение, повторная оплата, возврат, повторное предъявление. Не допускать многократной обычной оплаты одного и того же остатка.
6. LLM использовать точечно для неоднозначных текстов и документов после отбора кандидатов; кэшировать извлечённые факты. Массовое сравнение и арифметику выполнять кодом. Это рекомендация по срокам и воспроизводимости, не ограничение правил.
7. Отдельно хранить объяснение: правило, источник, кандидаты, уверенность. Итоговый CSV содержит только пять официальных полей.
8. Начать с sample, затем временной проверки на части TRAIN с корректным входящим остатком. При проверке не использовать golden проверяемого периода для выбора ответов. Labels нужны для обучения/оценки; LIVE/FINAL не должны зависеть от наличия golden.
9. Сравнивать общий score и сегменты; сохранять commit, время, параметры, hash файла, локальные/серверные метрики. Отправлять LIVE только содержательные изменения; оставить несколько слотов на интеграцию и формат.
