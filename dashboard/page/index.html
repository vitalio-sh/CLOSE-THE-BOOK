From bank movement to submission row

Each operation follows the same ordered checks. The first valid proposal is applied.

1

Read the source records

Bank movements, open balances, invoice registers, payment batches and remittance advice are loaded.
  • Opening balances carry forward what remains unpaid.
  • A later-dated invoice cannot be used for an earlier payment.
2

Try the matching methods in order

The first valid proposal wins: payment batches, remittance advice, accounting categories, then invoice matching.
  • Batch and advice records can explain one payment covering many invoices.
  • Invoice matching considers references, counterparties, amounts and policy rules.
3

Check the proposal

Before applying a proposal, the engine checks item identity, dates, duplicate rows and the available balance.
  • A rejected proposal lets the next method try.
  • If every method fails, the transaction stays unidentified.
4

Update balances in date order

Allocations reduce open balances. A returned payment reopens the applied amount; a duplicate payment does not reduce it again.
5

Validate and write the file

One CSV row is written per transaction–item allocation, or a category row when there is no invoice link.
  • Format checks run before the file is published.
  • The file hash identifies the exact output under review.
